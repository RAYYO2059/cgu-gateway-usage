# 上游的前置過濾：21,099 筆未進入本專案的資料

> **這份檔講的是「我們手上的東西是什麼」，不是分析方法。**
> 它影響的是**規模**與**成本**這兩個已交付的答案，所以獨立成檔——
> 讀成本數字的人不會翻 `ref/annotation_protocol.md`。
>
> 發現於 2026-09-08，來源是一次全量鍵掃描的副產品。
> **這個欄位在 manifest 裡存在整個專案期間**，而 repo 對
> `excluded_internal_prompts`、`141,619`、`21,099` 的全文檢索**零命中**——
> 也就是說它一直在那裡，只是沒有人打開過 manifest。

---

## 一、事實

來源：`data/00_raw_lite/<date>/<date>/_prepare_report.json`，23 份，
每個擷取日一份。這些檔與請求記錄放在同一批目錄裡，但**不是請求記錄**——
它們的頂層鍵完全不同，也因此在 `extract_lite.py` 的 `rglob("*.json")`
掃描裡不會產生任何一列（`request` 是空物件）。

```
source_files                 141,619
written_records              120,520
excluded_internal_prompts     21,099   （14.90%）
skipped_records                    0
failed_files / failures         0 / 0
```

**平帳等式成立：** `written + excluded + skipped = 120,520 + 21,099 + 0 = 141,619 = source_files`。
沒有第四類去向，也沒有失敗的檔。

23 份 manifest 的 `schema` 全部是 `ai_platform_request` `1.1-lite`
——與請求記錄同一個 schema 版本，所以這不是某一天的例外格式。

**每日的 `written_records` 與 L1 的列數逐日相符**（下表第三、四欄），
所以下面這張表是精確對照，不是估計。

## 三、已排除的一個候選解釋

**被移除的不是前置規則 3（工具自動發出）那一類。**

那兩天**保留下來**的資料裡，規則 3 的佔比高於其餘各天。若上游移除的是
同一個類別，保留資料裡的佔比應該更**低**才對。

**分母有兩種，兩種都列，因為它們給的數字不同：**

| 分母 | 07-30 | 08-03 | 其餘 20 天平均 |
| --- | ---: | ---: | ---: |
| 當日 `written_records`（＝表格第四欄的分母） | 9.9% | 11.8% | 7.6% |
| 當日**有前置規則判定**的列（排除 <20 字元與無 `prompt_text` 者） | 11.2% | 13.4% | 9.1% |

兩種分母的方向一致（受影響兩天都高於其餘），所以論證不依賴選哪一個。
**但兩個數字不可以混著引用**——本檔第一版就是一節用一種、另一節用另一種，
由測試的突變檢查撞出來。全母體 120,520 列裡有 13,527 列沒有前置規則判定
（內容 <20 字元或無 `prompt_text`），這就是兩個分母的差。
通則見 `docs/ENGINEERING_NOTES.md`〈並排的數字要標明各自的算法〉。

（這是排除一個候選，不是指認另一個。）

## 四、兩個無法區分的解釋

- **(a) 上游的排除規則在 08-04 前後改變。** 07-30 的 `source_files` 是 19,954、
  08-04 是 22,588，量級相當，卻一個排除 68.1%、一個排除 0.3%。
- **(b) 那兩天真的有一批 internal prompt 的爆量。**

**分不開，理由是被排除的記錄不在檔案裡。** 我們看得到的只有一個計數，
沒有任何一筆被排除記錄的中繼資料——連時間、模型、識別碼都沒有。
不管用什麼統計方法，**資料裡沒有可以區分這兩個解釋的變異**。
只能問上游。

## 五、影響清單

**這是清單，不是修改建議。** 每一項要不要改、怎麼改，需要先知道上游對
「internal prompt」的定義。

- **`120,520 筆` 是排除後的數字，不是 gateway 的流量。** 該期間通過的是
  141,619 筆（以 `source_files` 為準）。
- **`US,749.32` 不含那 21,099 筆的成本。** 這個數字目前標註為
  「牌價等值，非帳單」；**現在還要加一句「且非全量」**。
  被排除記錄的 token 用量完全未知，所以缺口的大小無法估計，
  連上界都給不出來。
- **`docs/data_lite/cost_by_day_lite.csv` 與 `docs/figures_lite/` 的日曲線
  有兩天被截斷**，其中一天是資料的第一天。表上看不出來。
- **24 天的期間敘述無誤**，但「每日用量」的可比性有兩天的缺口。
- **不受影響的項目：**
  - 73.12 小時服務中斷（台北 08-07 13:23 至 08-10 14:30）——那幾天排除為 0
  - 756 次限流（08-18 15:00 至 08-19 14:00）——排除為 0
  - 分類母數 17,365 的**內部**比例——全部在同一批 120,520 上計算，內部一致

## 六、待上游回覆的問題

逐條列出，可直接拿去問：

1. **`excluded_internal_prompts` 的定義是什麼？** 哪些請求會被歸為
   internal prompt？判準是欄位、來源、帳號，還是內容？
2. **這個排除規則在 2026-07-30 至 08-23 期間是否改變過？**
   若有，改在哪一天、改了什麼？
3. **07-30 與 08-03 的高排除率（68.1% / 73.8%）是規則的效果，
   還是那兩天的流量組成不同？**
4. **被排除的記錄是否另有留存？** 若有，能否提供其**中繼資料**
   （時間、模型、token 用量、匿名識別碼），不需要內容——
   有中繼資料就能補上成本與規模的缺口。
5. **被排除的記錄是否計入校方的實際帳單？** 這決定 `US,749.32`
   與帳單的差距是不是還要再加一項。
6. **clean 批（7 月）是否有同樣的排除？** 那批的 manifest 未檢查；
   若有，`turn_id` 那一組分析也要加同樣的但書。
7. **同一個排除是否也套用在 `prompt_text` 之內？**
   即：一筆被保留的記錄，其 `prompt_text` 是否也被移除過片段？
   這與 `ref/annotation_protocol.md` 第一節〈可分類母數 17,365 的
   可分類性上限〉是同一個問題的兩面。

## 八、那個假說能不能驗

**能，有三種方式，都用現有資料，不需要向上游要東西。**

1. **連續性檢定。** 若 08-04 起的規則 4 流量來自一個持續運作的產生器，
   它應該**每天都出現**，不是只出現在三天。若它只出現三天，
   「上游停止過濾之後它就一直看得見」這個說法就不成立。
   **這一項的輸入就在第二節那張表的最後兩欄裡**，成本是零。
2. **量級比對。** 被排除的 21,099 筆與規則 4 的 36,325 筆若同源，
   兩者的日均速率應該可比。可算，但只能否證不能證實——
   量級相符不排除巧合。
3. **形態比對。** 規則 4 的內容有固定的結構標記
   （`ref/prefilter_markers.csv` 的判定字串）。若上游願意提供
   被排除記錄的**任一項中繼資料**，就能直接比對。
   **但那已經不是「用現有資料」了**，屬於第六節的問題 4。

**本檔刻意不執行這三項。** 假說是在看到資料之後才形成的，
若同一輪就用同一批資料驗證它，那是自我驗證——
理由同 `ref/annotation_protocol.md` 第二節 (b)。
要驗就先寫定判讀規則，再驗。
