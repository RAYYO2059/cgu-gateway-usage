# 工程筆記

這份記的是**通用的規則**：換一個專案、換一批資料仍然成立的那些。專案特定的
判斷在 `docs/DESIGN_NOTES.md`（未隨 repo 公開）。

分家的判準就是上面那句話。一條規則如果只在這批資料的形狀下成立，它是判斷
不是規則。

**每一條都保留了原始案例。** 通用規則沒有具體案例會退化成標語——「要小心
分組計數」誰都會說，「四項相加比實際排除量多 3，成因是指派在請求層而去重在
內容層」才有辦法在下次遇到時被認出來。案例裡的數字來自 CGU AI Gateway 的
使用日誌分析（2026-07 至 08），不含任何個人資料。

共通的形狀：**這些錯誤都不會讓任何東西失敗。** 程式照跑、報表照出、測試照過，
只是數字不對。所以每一條的重點都不在「怎麼修」，在「怎麼讓它有機會被發現」。

# 計數與聚合

## 子集的筆數不得超過母體——量級大時自證，量級小時隱形

- **現象**：計算前置規則的命中量時，程式以 `startswith("tool_")` 掃欄位名，
  把 schema 本身的 `tool_count`（agent 的工具呼叫次數，整數欄）當成了標記
  旗標欄。`.sum()` 加的是**次數不是筆數**，算出「383,678 筆」——而母體只有
  106,993。
- **成因**：欄位以**命名慣例**辨識，而命名慣例沒有型別保證。同一個前綴底下
  混著布林旗標與整數計數，`.sum()` 對兩者都合法、都不會報錯。
- **含意**：這個錯誤之所以被發現，只是因為它產生了一個**不可能的數字**。若那
  支腳本的工具呼叫次數少一些、總和落在 10 萬以內，同樣的錯會靜默地讓 token
  佔比灌到 59%、成本多算約 $700，而數字看起來完全合理。**被發現是運氣，不是
  檢查。**
- **規則**：任何子集的筆數不得超過母體。這條檢查的成本幾乎為零，抓的是一整類
  錯誤——把數值當計數、重複計數、分組漏去重。已實作於
  `schema_lite.check_subset_counts()`，並以 `provider`／`request_style`／
  `date_taipei` 三個天然互斥分組在 `run_warning_checks()` 裡自我檢查：它們理應
  永遠通過，一旦沒通過就代表 groupby 或 dtype 出了更基本的問題。
- **限制（這條才是重點）**：**這條檢查只在量級明顯時有效。** 同一類錯誤在
  [指派層級與去重層級不一致]那次只多算 3，任何量級檢查都不會響。當時抓到它的
  是「四項相加不等於總數」這個**結構性矛盾**，不是數字看起來不合理。所以
  「數字看起來合不合理」不能當防線——要防的是結構，不是量級。
- **同類**：
  - [指派層級與去重層級不一致，會讓分組計數多算]——同一類錯誤的低量級形態。
    兩條放在一起才完整：一條講它大聲時怎麼抓，一條講它安靜時怎麼抓。
  - [測試可以驗一個永遠不會被執行的路徑]——三者的共同結構是：**檢查存在、
    也正確運作，但涵蓋不到實際出問題的那個情況。**

## 指派層級與去重層級不一致，會讓分組計數多算

- **現象**：分類母數 17,368 多算了 3，而它是後面所有比例的分母。正確值 17,365。
- **成因**：規則以**逐請求**指派，相異內容以**逐組 nunique** 計數。同一段內容
  若被不同模型送過（3 段內容各有 2 筆請求，一筆送向量模型、一筆沒有），它會
  同時落進「規則 1」組與「剩餘母數」組，兩邊各被數一次。**被重複計數的不是
  四條規則，是「剩餘母數」那一組**——四項的計數從頭到尾都是對的。
- **含意**：這個錯誤沒有任何檢查抓得到。母數是個合理的數字，四項也各自正確，
  分類器照跑、佔比照算。發現它的是「四項相加對不上總數」這個矛盾——而**該矛盾
  原本被歸因於四條規則互相重疊**，錯誤的歸因差點讓真正的成因躲過去：查證時
  重建了規則、確認規則互斥，才發現多出來的 3 根本不在規則那一側。
- **規則**：分組計數時，**指派層級與去重層級必須一致**。指派在請求層、去重在
  內容層的話，任何橫跨兩組的個體都會被多算。要嘛把指派提升到去重的層級（本例
  的做法：以 sha256 為單位指派，同一內容取優先序最高的規則），要嘛兩邊都用
  請求層。
- **同類**：與這次一起找回的那支腳本裡記著同一類錯誤的另一種形態——上一版用
  `startswith("tool_")` 掃欄位，把 schema 本身的 `tool_count`（整數欄）當成
  旗標，`.sum()` 加的是數值不是筆數，算出「383,678 筆」超過總筆數 106,993。
  **那次一眼就看得出來，這次只差 3。** 同一類錯誤在量級大時自證，量級小時
  完全隱形，所以不能靠「數字看起來合不合理」當防線。（那次事件目前只記在
  程式註解裡，尚未獨立成條。）

## 分類結果必須用兩個母數各報一次

**規則：每個分類指標都要用兩個母數各出一次，不要只出一個然後在註解說明。**

    相異 prompt 為母數 → 回答「校內有多少種不同的用法」
    請求數為母數       → 回答「負載與成本花在哪」

理由是同一批資料在兩個母數下會給出不同、而且都正確的答案。驗證集裡一支跑 74 次的
流水線，在相異 prompt 母數裡只算一票，在請求數母數裡抵得過 74 個一次性的人類提問。
150 個相異 prompt 代表 491 次請求，其中 64.7% 只出現一次——右尾把平均拉到 3.27，
是中位數的三倍多。

校方會問的兩個問題剛好各自落在一邊：「拿來做什麼」偏相異 prompt，「花了多少錢」
必然是請求數。**一張表答不了兩題**，而註解擋不住誤讀——讀者會記住表格裡的數字，
不會記住註解。

（另見「同一條流水線的版本迭代會膨脹相異 prompt 的計數」：相異 prompt 母數本身
也有它的偏誤，適合當分類成本的估計，不適合當活躍度指標。）

## 金額不補捨入殘差

clean 的 `_shares_exact` 把捨入殘差補進請求數最大的那一組，好讓比例欄加總
剛好 1.0000。**金額不套用這個做法。**

差別在兩者的身分不同：

    比例   是導出量，「加總為 1」是它的定義的一部分；
           把 0.0001 補給最大的那組，沒有任何一個事實被改動。
    金額   是事實。把 3 分錢塞給某個學院，那一列就不再是那個學院的實際金額
           ——為了讓表格看起來整齊，讓數字說了一件沒發生的事。

實測 `cost_by_unit_lite` 的七列相加是 $2,729.08、`cost_by_model_family_lite`
的六十列相加是 $2,729.10，而總額是 $2,729.09。差 1–3 分，來自每一格獨立
四捨五入到分。這個差異寫進 caveat，並在 `cost_structure_lite` 保留一列精確
總額供對照。

**寧可讓表格看起來不完美，也不要讓數字說一件沒發生的事。** 這條與既有幾條
同族——`UNMAPPED` 不寫 None、未定價不填 0、回填標 `backfilled: true`、
不補寫事後觀察——共同點都是：不要為了輸出好看而製造一個看起來正常的假值。

# 沉默的失效

## 穩定漏算比突發漏算更難發現

2026-08-27 補齊 18 個模型的牌價時發現的。這 18 個佔缺口 98.2% 的前四名——
`gpt-5.4-nano`、`gpt-4.1-mini`、`gpt-5`、`gpt-4o`——**全部是資料期間第一天就在、
且持續使用 14 到 18 天的模型**。只有剩下 1.8% 是後期才首次出現的。

這與直覺相反。「有模型沒有牌價」聽起來像「有新模型冒出來」，於是防護的設計會
往「偵測變化」的方向走——監看佔比跳升、看新出現的名字。但實際的漏算來自
**從頭到尾都在、只是量小到沒人看**的模型。

    突發漏算   有一個「出現」的時刻，佔比會跳，監控抓得到
    穩定漏算   沒有任何時刻。它從第一天就在分母裡，佔比是平的

平的東西不會觸發任何以「變化」為判準的警報。而它累積的金額不比突發的少——
這四個模型合計 8,688,632 token，佔應計費 token 的 0.21%，換算約 $19 的漏算，
在一批 24 天的資料裡。資料量放大十倍，它也放大十倍，而且仍然是平的。

**這是「把 unpriced_no_table 清到接近零」這個決定的真正理由，不是整潔。**
那個桶混著兩種東西：穩定漏算與新模型。混在一起時，桶裡有 40 幾個名字是常態，
於是沒有人會去看裡面是什麼；清到零之後，**任何非零都是事件**——而那一刻才分得出
它是哪一種（看它的首次出現日期）。

推廣：凡是「例外清單」型的診斷輸出，長期維持在非零就等於失效。判準不是
「例外多不多」，是「新的例外會不會被看見」。

## 保底寫成先給再扣就不是保底

- **現象**：兩支不相關的分層抽樣程式，各自為「每一層至少抽到一個」寫了
  保底，兩次都失效，兩次都不報錯。

  **(1) 驗證集抽樣（150 筆，24 層）。** 分配是

      alloc = {s: max(1, int(round(remaining * n / sizes.sum())))
               for s, n in sizes.items()}
      for stratum, want in alloc.items():
          if len(picked) >= N:
              break
          take = part.sample(min(want, len(part), N - len(picked)), ...)

  `max(1, ...)` 是保底。但 24 層各自向上取整之後，`alloc` 的總和大於
  `remaining`；而 `sizes` 來自 `value_counts()`，**迭代順序是由大到小**，
  於是大層先把名額吃完，走到小層時 `len(picked) >= N` 觸發 `break`，
  或 `min(..., N - len(picked))` 變成 `sample(0)` 回空表。
  **兩條路徑都不報錯。** 結果是 24 層裡 **4 層一筆都沒抽到**
  （合計 145 個相異內容、佔母體 0.84%），而這件事在抽樣當下沒有任何
  輸出提到它——是幾週後有人拿母體的層數去對樣本的層數才發現。

  **(2) 重篩抽樣（20 群，3 層）。** 分配先按比例、再對非空層補到 1，
  然後回收超配的部分：

      while sum(alloc.values()) > n:
          k = min((x for x in order if alloc[x] > 1 or sizes[x] == alloc[x]), ...)
          alloc[k] -= 1

  候選集合包含 `sizes[x] == alloc[x]` 的層，而剛被補到 1 的小層正好
  滿足它（`sizes=1, alloc=1`），於是保底當場被扣回 0。只在小層母體
  極小時觸發，被突變測試抓到。

- **共同形狀**：**保底先加進分配，再由某個回收／截斷／`break` 步驟拿走。**
  兩次的保底本身都寫對了，錯的是它之後還有一個步驟能碰它。
- **為什麼特別難發現**：失效條件是「小層」，而**小層正是保底存在的理由**。
  它在最需要的時候失效，而且失效的表現是「那一層沒有樣本」——與
  「那一層本來就沒東西」在輸出上完全一樣。
- **規則**：**保底名額先從總額扣除，剩餘才進入比例分配。**

      reserved = sum(1 for s in strata if size[s] > 0)
      alloc = 保底 1 each + 比例分配(n - reserved)

  任何在分配之後執行的回收、截斷、`break`，**都不得觸及保底的那一份**。
  若總額連保底都不夠（`n < reserved`），那是呼叫端要處理的錯誤，
  不是靜默地少抽幾層。
- **測試要涵蓋兩種邊界**：**小層母體極小**（`sizes = {1, 200, 2}`）與
  **保底總額接近或超過樣本數**（層數 ≥ n）。只測「正常比例」的分配
  永遠不會碰到這個 bug——兩次都是在正常比例下寫出來、也在正常比例下
  通過的。
- **推論**：寫「保底先扣除」的版本時又踩到第三次，形狀不同但同源。
  改寫後的斷言放在函式**最後**，於是把 `1 +` 拿掉之後**斷言仍然通過**——
  因為後面補足名額的迴圈，其排序鍵剛好會替每一層各補回一個。
  突變測試抓到的：那條突變一開始沒有任何測試變紅。

      # 錯：斷言在最後，被後續步驟意外「修好」
      alloc = {k: 1 + share[k] for k in reserved}
      ...補足迴圈...
      assert all(alloc[k] >= 1 for k in reserved)

      # 對：斷言在保證成立的那一刻
      alloc = {k: 1 + share[k] for k in reserved}
      assert all(alloc[k] >= 1 for k in reserved)
      ...補足迴圈...

  **斷言要放在被保證的性質成立的那一刻，不是放在函式出口。** 放在出口
  驗的是「最後有沒有成立」，而那可能是被下游某個步驟湊出來的；
  **保底若是靠某個後續步驟的巧合成立，它就不是保底，只是還沒失效。**

## 指標失敗會偽裝成正常報表

- **現象**：系代碼對照表補齊之後，`unmapped_dept_codes_lite` 變成空表。
  `pd.DataFrame(空 rows)` 推不出任何欄位 → `sort_values("n_requests")`
  拋 KeyError → 該指標判定為失敗、不寫 csv → 渲染器發現 csv 不存在，
  記一行 warning 之後**保留 RESULTS_lite.md 裡原本那張六列的舊表**。
  文件看起來完全正常，只是它描述的狀態已經不存在了。

- **成因**：三段行為單獨看都合理。指標失敗該報錯而不是靜靜產出半成品；
  渲染器找不到檔案時不覆寫，是為了避免一次失敗的執行把整份文件洗成空白；
  而舊表是有效的 markdown，沒有任何格式線索顯示它過期。串起來才是靜默的
  資料過期——**沒有任何一段需要修，錯的是它們的組合**。

- **含意**：渲染器「找不到就保留舊的」這個策略，在舊內容仍然可讀的情況下
  會把失敗偽裝成正常。保守的預設值在這裡反過來咬人：它保護的是「不要弄壞
  文件」，而代價是「不會告訴你文件已經不對了」。

  更值得記的是**觸發它的是一件好事**。這條路徑不是被錯誤觸發的，是被
  「缺口補完了」觸發的。任何「異常才會出事」的直覺在這裡都不成立——
  監測型指標的正常終點本來就是空表，那是它成功的樣子，不是失敗的樣子。

- **規則**：**監測型指標必須能處理空結果。** 三件事缺一不可：
  - 欄位寫死，不從資料推導（`UNMAPPED_COLUMNS`）。空表也要有表頭。
  - 空表要有明確的訊息，且與「執行失敗」在文字上分得開。共用的
    `render_block()` 對空表印「本次執行沒有資料」，那句話對監測指標是錯的
    ——它讀起來像跑失敗了。
  - 保留資料連結。只寫一句「這張表留著」卻沒有東西可以點，讀者分不出
    「留著」與「拿掉」。

- **同類**：與[穩定漏算比突發漏算更難發現]、
  [測試可以驗一個永遠不會被執行的路徑]是同一族。三者的共同結構是**機制存在、而且正確運作，只是涵蓋不到實際
  出問題的那條路徑**：前者的告警只認得變化不認得穩定的偏差，中間那條的測試
  驗的是一個沒有人會走到的分支，這一條的 warning 確實印出來了——印在 log 裡，
  而讀報表的人不看 log。

## 成本估算依賴分區欄，而分區欄不在檔案裡

- **現象**：查證第三節時，用 `glob` 逐檔 `read_parquet` 再 concat，算出來的總額
  是 **$2,754.80**；管線的正式輸出是 **$2,749.32**。差 $5.48，沒有任何錯誤或警告。

- **成因**：`data/01_request_lite/` 是 Hive 分區目錄（`date_taipei=YYYY-MM-DD/`），
  `date_taipei` 這一欄**不存在於任何 parquet 檔內**，只在用目錄路徑讀取時由
  pandas 從資料夾名產生。而 `pricing` 要靠它判斷請求落在 gpt-5.6-sol
  2026-08-22 降價的前面還是後面。少了那一欄，生效日分段靜默挑到另一組價目。

- **為什麼難發現**：挑錯價目不會拋例外，也不會讓任何欄位變成 NA。四段金額
  照樣加總等於總額，price_confidence 照樣四桶相加等於總額，**每一項內部
  一致性檢查都會通過**。唯一的訊號是跟另一個來源比對時差了幾塊錢。

- **規則**：任何重算一律走 `extract_lite.load_dataset()`，不自行拼接檔案。
  這條同時寫進 RUNBOOK_lite.md——它有一個對外的含意：**拿 `docs/data_lite/`
  的 csv 或原始 parquet 想自行重算的人會得到不同的數字，而他沒有理由知道
  要走那個函式。**

- **同類**：這是[穩定漏算比突發漏算更難發現]那一條的另一個實例。差別在於
  那一條的缺口在資料，這一條的缺口在**讀取方式**——同一份資料用兩種讀法
  得到兩個數字，兩個都「看起來對」。

---

## 快取的作用域要綁載入，不綁模組

`pricing.estimate_frame` 對 12 萬列逐列估算要幾秒，四個成本指標各算一次就是
四倍，所以要快取。**快取掛在 `load_tables_lite()` 回傳的 dict 上，不掛模組
全域。**

    掛 tables dict   壽命 = 一次執行。runner 每次執行都產生新的 dict，
                     下一次執行自然拿不到上一次的東西。
    掛模組全域       同一個行程裡換一批資料重跑，會拿到上一批的成本，
                     **而且不報錯**——它會安靜地回傳一組完全合理的數字。

第二種的危險不在於它會錯，而在於它錯了不吭聲。這與既有的兩個坑同族：

    part-<run_id>.parquet 不帶 chunk 序號 → 後一個 chunk 靜默覆蓋前一個
    overwrite_or_ignore                  → 寫入被忽略時不吭聲
    模組層級快取                          → 換了資料仍回傳舊值

三者都不會拋例外、不會缺欄位、不會讓測試變紅。**危險的不是錯，是不報錯的錯。**
判準因此不是「快取會不會失效」，而是「失效時看不看得出來」。

# 檢查與測試

## 兩道防線各管一件事：斷言擋門口，篩選擋範圍

`render_index.run()` 的 `assert line == "clean"` 與各函式裡的
`registry.list_metrics(line)`，看起來像重複，其實擋的是兩件不同的事：

    斷言        擋「呼叫端傳錯 line」        —— 門口
    list_metrics 擋「函式內部讀錯範圍」      —— 進門之後

19 → 23 那個事故是**後者**：呼叫端傳的是 clean、斷言完全放行，但
`build_index()` 內部讀的是全域 `registry.REGISTRY`，而 lite 的指標已經被
import 進來了。於是 INDEX.md 與 README.md 的「已註冊指標」從 19 變成 23，
沒有任何錯誤訊號。

**兩者不可互相取代。** 只有斷言的話，門內讀錯範圍照樣出錯；只有篩選的話，
呼叫端傳 lite 進來會讓整份 clean 文件被 lite 的內容填滿——那不是計數錯誤，
是整份文件錯了。

推廣：凡是「全域可變狀態 + 依參數篩選」的組合都適用。參數只保證呼叫端的
意圖，保證不了實作有沒有真的照那個意圖去讀。

## 測試可以驗一個永遠不會被執行的路徑

`tests/test_pricing_table.py` 有 14 個測試，全部通過。它們**沒有一個載入過
`ref/pricing_table.csv`**——每一個都用 `write_table()` 現場合成一張表再驗。

於是 2026-08-27 在價目表加了幾行 `#` 註解（純文件動作，一個數字都沒改）之後，
`PricingTable.from_csv()` 直接 raise——`csv.DictReader` 把第一行註解當成了標頭。
**而 14 個測試依然全過。**

這是「空真」（vacuous truth）的另一種形式，而且比典型的空真更難察覺：

    典型空真   斷言的前提永遠不成立（for x in []: assert ...），一條都沒跑
    這一種     斷言確實跑了、也確實正確，但**驗的對象不是實際會被執行的那個**

第二種在覆蓋率報告上看起來完全正常：`from_csv()` 有被呼叫、分支有走到、
斷言有通過。缺的是「用真實輸入呼叫它」這一次。

修法是最低限度的一條：**至少要有一個測試載入實際出貨的那個檔案**。已補三個——
載得起來、能算出正確金額（用 `gpt-4o` 的官方價逐段驗）、以及註解行沒有被當成
資料列。第二個是必要的：欄位齊全但價格全空的表也「載得起來」。

推廣：凡是專案會出貨的設定檔、對照表、schema 檔，都要有一個測試拿**真檔**去跑
一次真實流程。合成輸入驗的是邏輯，真檔驗的是「我們手上這一份能不能用」，
兩者不互相取代。

## 驗證指令本身要驗過

- **現象**：確認一個檔案有沒有被 `.gitignore` 擋掉，用的是
  `git check-ignore -v <path>`。它印出 `!ref/annotation_protocol.md`（否定
  規則，代表放行）**而 exit code 是 0**。若把「exit 0」讀成「被 ignore」，
  結論會與事實完全相反。
- **成因**：`-v` 回報的是**「有沒有規則命中」**，否定規則也算命中；`-q`
  回報的才是**「這個路徑是不是被忽略」**（0 = 被忽略，1 = 未被忽略）。
  兩個模式的 exit code 語意不同，而指令名字一樣。
- **實際是三態，不是兩態**：

      狀態                      -v 輸出              -v exit   -q exit
      未追蹤 + 被 ignore        印出 ref/*           0         0
      未追蹤 + 命中否定規則      印出 !ref/xxx        0         1
      已追蹤                    無輸出               1         1

  三種狀態、兩個 exit code，而且 `-v` 回 1 的是**「已放行且已進版控」**——
  它跟「未命中任何規則」（可能是路徑打錯、可能是白名單根本沒生效）撞在
  同一個訊號上。**最成功的狀態與最可疑的狀態給出同一個回覆。**
  （已追蹤的檔案根本不過 gitignore，所以 `-v` 什麼都不印，這一點與否定
  規則無關，卻讓 `-v` 的輸出「有無」也不能當判準。）
- **為什麼危險**：這條鏈上沒有任何一環會報錯。指令跑成功、輸出看起來相關、
  exit code 是個合法值——只是它回答的不是你問的那個問題。**驗收步驟出錯
  比被驗的東西出錯更難發現**，因為驗收本身就是用來發現錯誤的那一層。
- **規則**：**用一個指令當驗收之前，先確認它回報的是你要的那件事**，做法是
  拿**已知答案的反例**跑一次——而反例要**涵蓋所有狀態，不是兩個**。
  本條規則第一次被使用時，就在自己的反例驗證裡抓到自己的不完整：原本只
  對照了「被擋」與「放行」兩態，跑過之後才發現「已追蹤」是第三態，而且
  它與「未命中」共用同一個 exit code。**兩個反例證明得了「兩者不同」，
  證明不了「這個指令分得開所有情況」。**
- **這裡的正確判準**：要問「進版控了沒有」就用
  `git ls-files --error-unmatch <path>`；要問「會不會被 ignore」就用
  `git check-ignore -q`。`-v` 只適合拿來**看是哪一條規則命中**，不適合
  當是非題的答案。

## 啟動檢查要用實際執行的那條路徑

- **現象**：一支程式在啟動時確認外部指令存在，用的是
  `shutil.which("claude")`——**通過了**。第一次真的呼叫時
  `subprocess.run(["claude", ...])` 回
  `FileNotFoundError: [WinError 2] 系統找不到指定的檔案`。
- **成因**：兩者的判準不同。

      shutil.which()   查 PATH **並且查 PATHEXT** → 找到 claude.CMD
      CreateProcess    查 PATH，**不查 PATHEXT**   → 找到沒有副檔名的
                                                    bash shim，執行不了

  npm 在 Windows 上同時裝了 `claude`（bash shim，無副檔名）、`claude.cmd`
  與 `claude.ps1`。`which` 看到的是能跑的那個，`subprocess` 撿到的是不能
  跑的那個。
- **為什麼特別糟**：**啟動檢查存在的唯一理由，就是不要跑到一半才失敗**——
  「半途失敗的代價不只是重跑：已完成的部分已經花了錢，而失敗點在哪要看
  輸出檔才知道。」這個檢查用一個**大概等價**的查詢代替了真實路徑，
  於是它保證的那件事正好是它沒有驗到的那件事。
- **這是〈驗證指令本身要驗過〉的同族**：`which` 回報的是「PATH 裡找得到
  嗎」，不是「這樣呼叫跑得起來嗎」。同一個字被當成兩個意思用。
- **規則**：**啟動檢查要走真實路徑跑一次最小的實例**，不要用一個「大概
  等價」的查詢代替。這裡的正確寫法是把 `which` 的**回傳值**交給
  `subprocess` 用（而不是重新傳裸名字），並且在啟動時就用它跑一次
  `--version` 之類的最小呼叫。
- **推廣**：`os.path.exists` 不等於「開得起來」（權限、鎖定、symlink 斷掉）；
  `import x` 成功不等於「x 的那個功能可用」（選配相依）；連得上資料庫
  不等於「這個查詢跑得起來」（權限在表層級）。**存在性檢查與可用性檢查
  是兩件事，而前者比較好寫，所以它常常被寫成後者。**
- **推廣**：凡是「回報狀態」的指令都要問一次它回報的是哪一種狀態。同型的例子：
  `grep -q` 找不到時回 1（不是錯誤），`diff` 相同時回 0（不是失敗），
  `test -e` 對 broken symlink 回假。**把 exit code 當語意用之前，先讀它的定義。**

# 紀錄與可重現

## 通則：事後補寫的紀錄不是紀錄

這條與既有的幾個決定是同一件事，合併記成通則：

    UNMAPPED 不寫 None        「查不到學院」看得出來是查不到
    未定價不填 0              「沒有價目」看得出來是沒有價目
    回填標 backfilled: true   「這筆是補的」看得出來是補的
    事後補寫的紀錄不是紀錄     「當時沒記」看得出來是沒記   ← 新增

共同點是：**「不知道」必須看得出來是不知道。** 每一條的反面都不會報錯，
只會安靜地產生一個看起來正常的值——None 被 groupby 丟掉、0 被加總、
補的資料看起來跟原生的一樣、後補的觀察看起來跟當場的一樣。

**「未定價不填 0」在指標層也適用，而 `fillna(0)` 是它最常見的失效點。**
上游把話講得很細沒有用——`pricing.py` 特地設計了四值 `pricing_status`
（priced／local／non_token／no_table）來區分「不花錢」與「不知道」，而下游
`cost_by_model_family_lite` 一行 `_cost.fillna(0.0)` 就把四種語意壓回同一個
`0.00`。48 個模型族因此印出「成本 0.00」，其中 43 個的真實情況是「我們算不
出來」。

這個失效比上游填 0 更難發現，因為**上游的欄位仍然是對的**：`pricing_status`
好端端地寫著 `unpriced_no_table`，任何檢查那一欄的測試都會通過。錯的是另一欄，
而那一欄看起來完全正常——0.00 是個合法金額。

實作上的分工寫成兩個函式：加總用的欄位可以 `fillna(0)`（總額因此是**下界**，
這句話跟著每一個總額走），顯示用的值一律走 `group_cost()`，它按
`pricing_status` 決定回傳實際金額、0 或 NA。**「某一列是 NA」與「總額偏低」
是同一件事的兩面**——逐列看得出哪些不知道，加總時那些不知道被當成 0。

判準：看到 `fillna(0)` 就問一句「這個 0 之後會被誰讀？」。被加總器讀沒問題，
被人讀就是假值。

新增這條的場合：整理 150 筆驗證集的標註筆記時，有 16 筆當時沒有留下個別
觀察。要不要現在重讀一次補上？**不補。** 補寫等於現在重新讀一次再造一個
「當時的觀察」，那不是保存，是杜撰——而且事後補的那一筆看起來會跟當場記的
完全一樣，讀者無從分辨哪些是標註時真的注意到的、哪些是事後為了填滿表格
生出來的。

差別在後續用途上是實質的：標註筆記的價值在於記錄**當時**的判斷困難，
它是用來檢討判準的。混入事後補寫的內容之後，「哪些形態當時難判」這個
問題就再也答不準了。

所以那 16 列留「—」，並在文件開頭寫明「其餘 N 筆當時無特別記錄」。
留白是資訊，填滿不是。

## 進入文件的數字，其產生程式必須在版控內

- **現象**：文件引用了一個不存在的模組（`markers.py`），且同一份文件對同一組
  標記給出「七種」與「八種」兩個數字。
- **成因**：那個判斷是在 session scratchpad 的一次性腳本上做的。腳本隨 session
  結束而消失，文件保留了**判斷結果**卻沒有保留**判斷依據**。兩個數字則是各數
  各的集合，寫的時候都對，事後沒有一處說明在數什麼。
- **含意**：本專案其他數字都能從 repo 重算——指標有 `src/metrics*/`、成本有
  `ref/pricing_table.csv`、學院有 `ref/college_mapping.csv`。**只有這一組不能，
  而它是分類母數的定義：母數錯了，後面每一個比例都跟著錯，且分類器照跑、
  佔比照算，沒有任何檢查會失敗。**
- **發現的時機是偶然**：追查「四項相加比實際排除量多 3」時撞見，不是任何檢查
  抓到的。沒有那 3 的話，這件事會一直不被發現。
- **規則**：任何進入文件的數字，其產生程式必須在版控內。**scratchpad 的一次性
  腳本若產生了要引用的數字，該腳本就不再是一次性的**——當下就要搬進 `src/`，
  不是等到需要重算時再說。判定用的對照資料同理，放 `ref/`。
- **適用範圍不只程式，連「這個數字為什麼錯」的描述也一樣。** 383,678 那次
  （見[子集的筆數不得超過母體]）的成因描述當時寫在 session scratchpad 那支
  腳本的註解裡，session 結束即消失。它現在還在，只是因為 Claude Code 的
  file-history 恰好留了一份——那是運氣，不是保存機制。**事故的描述比事故的
  數字更難重建**：數字還能重算，描述一旦沒了就只剩「當初好像有這回事」。
- **同類**：與[穩定漏算比突發漏算更難發現]同一種失效——沒有任何時刻會出錯，
  所以沒有任何時刻會被注意到。差別在於那一條的隱形來源是資料的形狀，這一條
  的隱形來源是我們自己的工作方式。

## 修正過的數字會退回去

- **現象**：「90.3% 的 prompt token 為快取讀取」在寫第一節時已查證並修正為
  **88.30%**，PROGRESS.md 存的就是 88.30%。三天後寫第三節的草稿又寫回 90.3%。

- **成因**：數字是從**對話歷史**取的，不是從檔案取的。歷史裡兩個版本都在，
  而錯的那個出現得比較早、被複述的次數比較多。修正只改了檔案，沒有也不可能
  改掉歷史。

- **為什麼兩道防線都擋不住**：
  - `prose_numbers` 只列出散文裡的數字，**不與任何來源比對**——它能告訴你
    「這段話裡有 90.3%」，不能告訴你 90.3% 是錯的。
  - 人也擋不住，因為 90.3% 和 88.30% 都是合理的數字。錯的版本沒有任何
    「看起來不對」的特徵，它只是不等於檔案裡的那個。

- **規則**：**文件中的每一個數字都以檔案為準，不以任何中間過程為準**——不以
  對話歷史、不以先前的草稿、不以自己上一輪算過的結果。查證的動作是「打開
  檔案讀出來」，不是「回想我算過多少」。

- **推論**：這使「補寫等於現在重新讀一次再造一個當時的觀察」那一條有了對稱的
  第二半。前者說的是**不要從記憶造事實**，這一條說的是**不要從記憶取數字**。
  兩者的共同結構是：歷史是一份未經修訂的紀錄，它保存錯誤的忠實程度與保存
  正確的完全相同。

# 辨識與去識別

## 偵測「同一支程式」要用框架，不要用完整字串

這個模式已經出現三次，值得寫成通則：

    客戶端框架文字   固定英文開頭句 + 每次不同的對話內容
    分類器外殼       固定分類樹 + 每次不同的 DATA 區塊
    側寫更新器       固定欄位名 + 每次累積更長的互動紀錄

三者的共同結構是**固定的外框加上會變的內容**。要認出「這是同一支程式發的」，
判準必須落在**外框**上；用 sha256 清單認的話，內容一變雜湊就變，清單當場失效。

危險的地方在於**失效沒有徵兆**：漏掉的請求不會報錯、不會缺欄位，它們只是安靜地
落進「需要人工判斷」那一堆，讓母數看起來比實際大、讓某一類的佔比看起來比實際小。
前置規則 3 與 4 都是照這條寫的，抽樣排除規則也是。

## 去識別的失效有兩個方向

`dept_code` 03/04 分不出醫技系與醫放系，是**分不開**：遮罩把兩個系合併了。

形態描述則是相反的方向——**分得太開**。在「1 個 uid 就構成一支流水線」的
母體裡，「某人同時在做 A 和 B」這種描述不含姓名、不含帳號、不含任何識別欄位，
卻足以指認到人，因為那個組合在全校只有一個人符合。

    分不開   遮罩合併了本來不同的個體 → 統計失真、無法歸屬
    分得太開 屬性組合唯一到足以指認   → 再識別風險

兩者都是去識別失效，但**補救方向相反**：前者要補資料（更細的代碼表），
後者要減資料（不發布形態組合）。把它們當成同一個問題處理，會得出「資料
不夠細」與「資料太細」互相矛盾的結論。

這是 `docs/CLASSIFICATION_NOTES.md` 進 `.gitignore` 的理由。該檔逐筆記錄
150 個樣本的形態，任何一列單獨看都無害，整份的價值恰恰在於它把形態組合
攤開——而那正是第二種失效的定義。

## 兩條關於「用 AI 建流水線」的方法學觀察

**(a) 上游的錯誤會被原樣傳下去，而且每一步看起來都正常。**
觀察到一條論文處理流水線：章節切分把一個參考文獻編號當成了章節標題，下游的摘要
環節仍照常為它產生了一段摘要。兩個環節各自都「成功」了，沒有任何一步會失敗。

這是「用 AI 串流水線」這個模式的普遍風險，不是個別疏失：每一段都被要求「根據給定
素材產出結果」，而沒有一段被賦予「這個輸入本身是不是有問題」的職責。要擋這種錯，
必須有一步明確負責質疑輸入，而那一步的成本與價值都不會出現在單段的評估裡。

**(b) 同一條流水線的版本迭代會膨脹相異 prompt 的計數。**
觀察到一支審查器在樣本期間內被改版——新增了一個「前後文」區塊與一條新判準。不同
版本是不同的 sha256，在相異 prompt 的母數裡各算一筆。

含意：報告若要講「哪條流水線最活躍」，必須區分**送出次數多**與**版本迭代多**。
後者是開發活動不是使用量，兩者混在一起會讓「還在調整中的流水線」看起來像
「被大量使用的流水線」。相異 prompt 數適合當分類成本的估計，不適合當活躍度指標。

## 明文邊界要涵蓋例外訊息

處理受限內容（個資、臨床紀錄、憑證）時，通常會明確規劃「哪些變數可以印」。
規劃的對象是**正常輸出路徑**——而例外訊息是另一條路徑，它會夾帶觸發它的資料。

    json.loads(bad_text)   → JSONDecodeError 的訊息含出錯位置附近的原文
    KeyError(payload_key)  → 例外物件本身就是那個值
    傳到頂層的 traceback   → 每一層 frame 的區域變數都可能被格式化出來

三者都不是「輸出內容」的程式碼寫的，所以逐行檢查輸出敘述時看不到它們。
**正常路徑防住了不代表防住了。**

規則，在禁止輸出明文的場合：

- `except` 區塊只印**型別名**（`type(exc).__name__`），不印 `str(exc)`、
  不印 `repr(exc)`、不印例外物件本身
- 不 `raise` 到頂層。讀不到、解析失敗一律**計數並繼續**，最後只報總數
- 失敗計數要報出來。安靜跳過會讓「全部讀成功」與「全部讀失敗」看起來一樣
- 這條對**日誌**同樣成立：`logger.exception()` 會寫 traceback 到日誌檔，
  而日誌檔通常不在明文邊界的規劃裡

代價是除錯變難——只有型別名沒有訊息。這是刻意的取捨：**明文一旦落地就收不
回來**，而除錯資訊可以在受控環境重跑一次拿到。若真的需要細節，讓失敗的
識別碼（雜湊、路徑）進日誌，內容不進。

**一則實例，出現在寫這條規則的那支程式裡。** 該程式的週期性檢查寫的是

    try:
        probe = blindness_check(flags, workdir)
    except SystemExit as exc:      # ← 只擋 SystemExit
        ...停止並記錄...

而 `SystemExit` **不是 `Exception` 的子類**（它直接繼承 `BaseException`）。
所以這個子句只擋自己主動拋的那一種，其餘例外——`FileNotFoundError`、
`JSONDecodeError`、`TimeoutExpired`——**全部漏過去帶著 traceback 跑到頂層**，
而那條路徑上的區域變數含提示詞與前綴。

同一支程式的啟動檢查更直接：完全沒有 `try`。實際跑的時候就炸出一個
完整 traceback（那次剛好只夾帶檔案路徑，但那是運氣不是設計）。

正確寫法：`except (SystemExit, Exception) as exc:`，並在子句裡分開處理
——自己拋的 `SystemExit` 訊息是自己寫的可以印，其餘只印 `type(exc).__name__`。

**推論：檢視 `except` 子句時要問的不是「這個型別對不對」，是「哪些型別會
從這裡漏出去」。** 前者只看得到寫下來的那一行，後者才看得到沒寫的那些。
Python 裡最常漏的三個是 `SystemExit`、`KeyboardInterrupt`、
`GeneratorExit`——它們都不是 `Exception`。
