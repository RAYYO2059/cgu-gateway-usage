## 摘要

本文件為 CGU AI Gateway 於 2026-07-30 至 2026-08-24 期間的使用情形
分析，涵蓋上游過濾後的 120,520 次 API 呼叫、357 個使用者識別碼。

**規模與成本。** 可歸屬到自然人的請求為 60,445 筆（50.15%），其餘來自
服務憑證。牌價等值成本合計 US$2,749.32，其中近半數（47.22%）為快取
相關成本——成因為請求模式而非模型單價。上游另排除 21,099 筆來源記錄，
因此請求與成本數字均非全量；排除記錄的 token 用量未知。

**單位分布。** 各單位的使用量差異，部分來自單一群組的集中使用而非該
單位的整體行為。四個學院中有兩個，其最大的單一遮罩帳號佔該學院六成
以上的請求，最高者近八成。

**使用類型。** 四條前置規則偵測到 13,646 個相異內容、48,893 筆請求；
這是可重現的流量性質，不是全量用途分布。分流層兩模型僅 31/58 群同值；
domain 逐筆交叉為 495/600，同時保留無法判定與規則邊界的異常。
這些結果沒有獨立人工真值，第四節說明做到哪裡、為什麼停在那裡。

**資料內容。** 日誌中包含多類第三人資料——病人臨床紀錄、具名醫護人員、
學生同儕的通訊軟體對話、住戶的設備位址與房號。其當事人均非本 gateway
的使用者，未曾亦無從提供同意。另有一項校內服務的存取權杖隨客戶端自動
附加的瀏覽器狀態進入日誌。

各項的限制與可回答程度見 1.4 與第六節。clean／lite 已發佈指標由管線
產生；第四節另列規則指派與探索性模型估計，來源和分母見
[docs/INDEX.md](INDEX.md)。

## 一、資料範圍與涵蓋率

### 1.1 期間與規模

資料期間為台北時間 2026-07-30 至 2026-08-24，共 26 個曆日，其中 24 日
有資料。2026-08-08 與 08-09 無任何請求紀錄——經查證為服務中斷，非資料
缺漏：中斷前最後一筆在 UTC 2026-08-07 05:23，之後第一筆在 08-10 06:30，
實際長度 73.12 小時。兩端邊界換算成台北時間分別是 13:23 與 14:30，均落在
日中而非日界，且上游處理報告記錄的跳過與失敗筆數均為零。

期間內共 120,520 次請求，日均 5,022 次。

最後一日（08-24）僅有 232 筆、9 個識別碼，且只涵蓋台北時間 00:00 至
01:48。這是資料範圍的邊界效應，不是使用量下降，成因有兩層：上游以 UTC
日期為單位交付，而本分析以台北時間分區，台北時間早 UTC 8 小時，因此
一個台北曆日橫跨兩個 UTC 交付單位；末日只取得到最後一個 UTC 單位的
前 8 小時，而該單位本身也止於 UTC 17:48。

同樣的邊界效應也出現在首日（07-30，只涵蓋台北時間 08:00 之後）與中斷後
的第一日（08-10，只涵蓋 14:00 之後）。24 個有資料的曆日中，這 3 日各只
取自單一 UTC 交付單位；其餘 21 日的**時間視窗**均橫跨兩個交付單位、
涵蓋完整的台北曆日，但這不表示上游沒有在其中排除記錄（見 6.5）。

### 1.2 識別碼組成

357 個識別碼並非 357 個人。組成為三類：

- 學生 155 個，37,921 筆請求
- 教職員 120 個，22,524 筆請求
- 服務憑證 82 個，60,075 筆請求

服務憑證（`link-*`、`open*` 形式）為程式帳號，非自然人。它們佔識別碼
總數的 23%，但佔請求總數的 49.85%。扣除之後，可歸屬到自然人的識別碼
為 275 個——本文件所有人均指標的分母都是這個數字，不是 357。

識別碼與遮罩帳號之間並非一對一。119 個相異遮罩帳號中，有 39 個對應到
多於一個識別碼。原因是遮罩一律替換帳號末三碼，但那三碼在兩種帳號裡的
意義不同：對學生而言是班級序號，所以碰撞的是同系、同學位、同入學學年的
使用者；對教職員而言只是流水號的低位，碰撞不承載任何單位意義。兩者的
形態差異見 2.2。反方向則為單值：每個識別碼恰對應一個遮罩帳號。

此不對稱決定了本分析的粒度上限：識別碼可歸屬到系所與學院，但遮罩帳號
無法回推到特定個人，因此 275 也是自然人數的上界而非精確值。詳見 6.1。

資料檔：

- [`docs/data_lite/requests_by_unit_lite.csv`](data_lite/requests_by_unit_lite.csv)
  — 各單位的帳號數與請求數；服務憑證那一列說明「357 個 uid ≠ 357 人」

### 1.3 可歸屬比例

單位別分析的母體為 60,445 筆（50.15%），即學生與教職員的請求總和。
其餘 60,075 筆來自服務憑證，無對應之自然人。

本文件因此使用兩套分母，各表均標示所用者：

- 全部請求 120,520 筆：用於成本總額、模型分布、時段分布
- 可歸屬請求 60,445 筆：用於單位佔比、人均、身分別比較

服務憑證的成本計入總額，但不計入任何人均指標——它沒有可作為分母的
自然人數。在 2.1 的表中，服務憑證的「佔可歸屬流量」欄顯示為「不適用」，
與被抑制的「—」意義不同：前者為不在母體，後者為算得出但不公布。

資料檔：

- [`docs/data_lite/unit_coverage_lite.csv`](data_lite/unit_coverage_lite.csv)
  — 四層覆蓋缺口：可歸屬個人 vs 服務憑證、學生能否歸到學院、教職員的資料層缺口

### 1.4 三項提問的可回答程度

| 提問 | 可回答程度 | 限制來源 |
| --- | --- | --- |
| 各學院／職員的使用情形 | 部分。最小可靠粒度為學院，母體為 50.15% 的請求 | 帳號遮罩；教職員帳號格式不編碼單位 |
| 使用類型 | 前置規則可報流量性質；domain 有探索性模型估計，無正式用途分布結論 | 分流層未通過交叉檢查；domain 無獨立人工真值，且有未釐清的判讀異常 |
| 成本 | 可回答已交付記錄的牌價等值金額；非實際帳單，且非全量 | 日誌無金額欄位，須以公開牌價回推；上游另排除 21,099 筆 |

三項限制的性質不同：身分與成本受資料欄位及上游交付範圍所限；
用途還受可見文字的涵蓋範圍與判定可靠度所限。交叉一致率不是正確率，
不能把探索性模型標籤升格為校內真實用途比例（見第四節與第六節）。

上表把 2.1 的請求量拿掉，只留身分結構。`帳號數` 數的是識別碼，`遮罩帳號數`
數的是遮罩之後還分得出來的組數，兩者的差距就是遮罩造成的碰撞（見 1.2）。
`最大帳號下帳號數` 是最大的那個遮罩帳號底下掛著幾個識別碼——它是解讀
`最大遮罩帳號佔比` 的必要條件：同一個佔比，底下是一個人與是十七個人，
意義完全不同。

2.1 的最後兩欄則是兩種不同的集中度。`最大單一帳號佔比` 數的是識別碼：
該單位內最大的單一識別碼發出多少比例的請求；`最大遮罩帳號佔比` 數的是
遮罩帳號。兩欄相等，
代表最大的那個遮罩帳號底下只有一個人；差距愈大，代表該單位的流量愈集中在
同系、同學位、同入學學年的同一群人身上。

醫學院與管理學院是上表的兩個極端，而它們的識別碼數相同（各 33 個）。醫學院
的 33 個識別碼分散在 31 個遮罩帳號，最大的那個底下只有一個人，所以它在 2.1
的兩欄佔比相同（均為 16.79%）——該學院的數字是 33 個人的加總。管理學院的
33 個識別碼只落在 12 個遮罩帳號，最大的一個底下有 17 個識別碼，超過該學院的
一半（17/33 = 51.5%），而這一群發出該學院近八成的請求（78.69%）。管理學院
那一列的「學院」數字，實際上主要在描述一個班。

工學院的最大遮罩帳號底下同樣有 17 個識別碼，但只佔該學院 30.90% 的請求。
兩個學院的 17 是巧合：底下掛著幾個人，與那群人用得多兇，是兩件要分開讀
的事。

服務憑證是第三種形狀——它的最大遮罩帳號只對應 1 個識別碼，卻佔 68.91%
的請求。那不是一群人，是單一自動化流程。也因為不是人，集中度規則不擋它的
佔比；母數門檻則照常適用。

教職員是第四種，而它與前三種都不同。該類的最大遮罩帳號底下有 29 個識別碼、
佔 45.01% 的請求，兩個數字都比任何一個學院高；120 個識別碼只落在 20 個遮罩
帳號，平均每組 6 個，碰撞率也是全表最高（學院裡最高的智慧運算學院是 4 個）。
但**這裡的碰撞不承載意義**：教職員帳號的格式是固定前綴加六位流水號，不編碼
所屬單位（見 2.3），所以那 29 個識別碼的共同點只是帳號號段相近，不是同系、
同學位、同入學學年。學院列的碰撞可以讀成「一個班」，這一列不行。

45.01% 因此不該讀成「有一個單位在密集使用」。它描述的是一段號碼區間，而
號碼區間不對應任何組織單位。

**這種集中不是抑制條件。** 抑制規則處理的是再識別風險，判準為母數
（`n_users` >= 10）與單人集中度（`top1_user_share` <= 30%）。四個學院均
通過：醫學院 16.79%、工學院 8.48%、管理學院 23.85%、智慧運算學院 23.35%，
母數 24 至 65 人。集中在一個遮罩帳號底下的是一群人而不是一個人，不構成
再識別風險，所以不遮蔽；但它使該單位的數字無法一般化到整個學院，所以要
標註。兩者的補救方式相反：前者是遮蔽，後者是標註。

### 2.3 未歸屬項目

本期間內全部學生識別碼均已歸屬到學院。系所代碼與學院的對照見
[ref/college_mapping.csv](../ref/college_mapping.csv)，共 28 個代碼、
25 個系所身分、4 個學院。

代碼數多於系所身分數，因為部分系所在不同學制使用不同代碼：生醫（學士 09、
碩博士 01）、醫工（26、31）、人工智慧（28、61）。對照表以 `dept_key` 欄
標記系所身分，該欄用於判定單系學院等以系所為單位的性質。

仍有兩類請求無法歸屬到學院。

**教職員，120 個識別碼、22,524 筆。** 教職員帳號格式為固定前綴加六位
流水號，不編碼所屬單位。此為上游帳號系統的欄位設計，補充對照表無法解決。

## 三、成本

### 3.1 總額與定義

牌價等值成本合計 US$2,749.32。

此金額的定義為：以日誌記錄的 token 用量，乘以 OpenAI 於 2026-08-27 查得
的公開牌價（Standard 級距）所得之等值金額。日誌不記錄金額，故無法自
資料直接取得實付費用。

本金額與實際帳單或全量流量成本的差異來源包括：

| 因素 | 影響 |
| --- | --- |
| 服務級距 | 日誌無 `service_tier` 欄位，本估算假設全部為 Standard。若實際使用 Batch 或 Flex（半價），本估算高估約一倍 |
| 區域處理加價 | 2026-03-05 後發布的模型若走資料落地端點加收 10%，無法自資料判定 |
| 機構折扣 | 若學校與供應商另有議價，牌價非實付價 |
| 促銷價時效 | 部分模型的現行價格為促銷價，官方標示至少維持至 2026-11-21 |
| 上游未交付記錄 | 23 份擷取報告合計排除 21,099 筆；本估算沒有這些記錄的 token 用量，無法估算缺口大小 |

促銷價時效使本指標具有一項本專案其他指標所無的性質：它是「資料 × 外部價目 ×
取價時間」的函數，而非僅為資料的函數。同一批資料在不同時間以更新的價目
重算會得到不同結果。引用本金額時應一併註明取價日期（2026-08-27）、
牌價等值非帳單，以及上游過濾後非全量的範圍（見[第六節](#六已知限制)）。

價目表見 [ref/pricing_table.csv](../ref/pricing_table.csv)。金額的完整結構
見 3.2 的表，該表的「總金額」列為本專案唯一的精確總額；各節分組表的逐列
金額獨立四捨五入到分，加總會與之相差一至數分。

快取相關（讀取加寫入）合計 47.22%。

成因為 agent 型客戶端的請求模式。此類客戶端在單次使用者操作中會發出

提供快取機制：首次送出時寫入快取（單價為一般輸入的 1.25 倍），後續送出

模式所需的內容重送。同一份工作若以較少次數的請求完成，快取相關成本會
顯著降低。

單次操作內部的請求展開情形，本批資料無法量測——lite schema 不含
`turn_id`，無對話結構。該項量測見 [RESULTS.md](RESULTS.md)，其資料為
2026-07-21 至 07-23、9,937 筆，含對話結構。

### 3.5 價格可靠度

3.4 說明的是哪些請求算不出金額。本節說明已算出的金額，其價格來源的
可靠程度。

價目來源分四類，依金額加權：

| 類別 | 金額 | 佔比 | 意義 |
| --- | --- | --- | --- |
| confirmed | $2,156.29 | 78.43% | 官方頁面明列 |
| inferred | $372.40 | 13.55% | 依規律推得，官方未直接列出 |
| promotional | $193.85 | 7.05% | 官方明列，但為有時效的促銷價 |
| provisional | $26.78 | 0.97% | 模型名稱與價目列的對應存在歧義 |

分類掛於個別價位而非整列價目。一列價目含四個價位（輸入、快取讀取、
快取寫入、輸出），四者的來源可以不同，故同一筆請求的金額可能分屬多個
類別。3.2 表中 `price_confidence` 區塊的「涉及筆數」欄跨列相加會超過
總筆數，此為預期行為。

此設計並非一開始如此。初版將分類掛於整列，`inferred` 因此顯示為 51.8%
（$1,424.65）——推估的只是該列四個價位中的一個，卻使整列的金額全數計入。
按價位加權後為 13.55%。前者會使讀者認為半數金額建立在推估之上。

**`inferred` 的組成。** $372.40 全部來自單一價位：`gpt-5.6-sol` 於
2026-08-22 降價前、短上下文級距的快取寫入價（長上下文那一列官方有列，
標記為 confirmed）。官方頁面僅列現價，該日之前的價格依同家族三個模型
（`gpt-5.6-sol`、`gpt-5.6-luna`、`gpt-5.6-terra`）「快取寫入為一般輸入
1.25 倍」的一致規律推得——該比例在表中八列有快取寫入價的價目上無一例外。

此為本估算最大的單一不確定來源。它影響總額的 13.55%：若該推估完全錯誤
而該段金額實為零，總額會從 $2,749.32 降為 $2,376.92，即現有總額有 13.55%
建立在這一個推估上。（反向的說法是：以 $2,376.92 為基準，現有總額高出
15.67%。兩個百分比描述同一件事，分母不同。）

**`promotional` 的時效。** $193.85 為 `gpt-5.6-sol` 降價後的價格，官方
標示至少維持至 2026-11-21。該日之後以更新的價目重算會得到不同金額，而
資料本身不變。

**`provisional` 的歧義。** $26.78 來自三個模型，但金額高度集中：

| 模型 | 金額 | 歧義的性質 |
| --- | --- | --- |
| `gpt-5.2-chat-latest` | $26.03 | 官方表格把 `chat-latest` 列在 ChatGPT 分類下（5.00/0.50/30.00），而 `gpt-5.2` 本身為 1.75/0.175/14.00，相差約三倍。目前照前者填 |
| `chat-latest` | $0.75 | 浮動別名，指向的實際模型會改變，而 lite schema 無 `response_model` 欄，無法逐筆確認 |
| `text-embedding-ada-002-v2` | $0.00 | 資料中的家族名帶 `-v2` 後綴，官方頁面只列不帶後綴者。期間內僅 1 筆 |

三者的性質不同：第一個是**同一個名字對到兩種價目**，第二個是**名字對到

## 四、用途分類的可回答界線

### 4.1 可重現的流量性質

四條現行前置規則偵測到 **13,646 個相異內容／48,893 筆請求**，分別佔
長度達 20 字元母體的 44.0%（13,646/31,011）與 45.7%（48,893/106,993）。
對同一凍結輸入連跑兩次，31,011 個內容的逐筆規則指派完全相同，
重現性為 **31,011/31,011（100%）**。在本節各分類層裡，只有這部分
量到逐內容指派的 100% 重現性。這是規則輸出的重現性，
不是用途分類正確率；規則描述的是已偵測流量的性質，不是誰的用途
（逐項計數與重跑檢查見 [CLASSIFICATION_LIMITS.md](CLASSIFICATION_LIMITS.md)）。

### 4.2 母數的形成與現行規則

**去重。** 120,279 筆有內容的請求對應 33,666 個相異內容，重複率 72.0%。
同一內容可以對應多筆請求，分類樣本以相異內容為單位；120,279 已扣除
241 筆內容缺值的請求，不再重扣（見 6.5）。

**長度下限。** 排除 20 字元以下的內容，相異內容減為 31,011（減少 2,655 個）。
被排除者多為接續訊號，不含足以判定用途的資訊。

**前置規則。** 前兩條依模型類型與端點資訊，後兩條依請求文字的框架標記；
後者是**內容判定，不是中繼資料判定**。下表只記現行規則偵測到的數量：

| 規則 | 現行判定依據 | 相異內容數 | 對應請求數 |
| --- | --- | ---: | ---: |
| 向量化 | embedding 類模型 | 587 | 1,010 |
| 影像生成 | 影像類模型 | 401 | 442 |
| 工具自動發出 | 請求文字含客戶端框架標記 | 2,387 | 11,116 |
| 流程中繼處理 | 請求文字含特定自動化流程的固定框架 | 10,271 | 36,325 |
| **合計** | | **13,646** | **48,893** |

四條規則使 31,011 個相異內容減至 **17,365** 個需逐筆判 domain 的內容，
對應 **58,100** 筆請求。**2,387 與 10,271 是現行規則偵測到的數量，
不是所有工具流量的完整計數。** `ref/prefilter_markers.csv` 的九條判定字串
含一條明確不攔的排除項；規則優先序、逐內容指派與計數由
`python -m src.classify_lite.prefilter` 固定。這些機械規則不需送模型判定，
但「沒有命中」不等於該內容確實不屬於工具或中繼流量。

### 4.3 分流層為什麼不能當用途來源

同提示詞與字典下，Opus 和 Codex 在分層抽出的 58 個 clean 群中，
`disposition` 只有 **31/58（53.4%）** 同值。這是兩模型交叉一致率，
不是與人工真值比較的正確率，也不能按分層樣本比例直接外推至全部群。

機械判準亦無法重現兩模型的共識：兩模型都判為 `tool_injected` 的 11 群中，
3 群的 `(uid數, unit_type種類, model種類)` 是 `(1,1,1)`；其餘 47 群中
也有 17 群三欄完全相同。任何只看這三欄的確定性規則，必須把這
20 群給同一結果，不能同時重現目前的共識／非共識分組。這是輸入特徵
不可分，不是換門檻即可修復的統計精度問題。分流層因此只留作探索材料，
不報群級的用途來源比例（見 [CLASSIFICATION_LIMITS.md](CLASSIFICATION_LIMITS.md)）。

舊 150 筆人工驗證集已遺失，而且原抽樣依賴 17,368 的舊母數，與現行
17,365 不同；保留下來的逐筆觀察不能重建樣本或充當現行參考標籤
（見 [annotation_protocol.md](../ref/annotation_protocol.md) 的母體座標）。
現階段沒有獨立人工驗證可把模型一致率換算成分類正確率。

### 4.4 逐筆 domain 的探索性模型估計

從前置規則後的 **17,365 個相異內容／58,100 筆請求**分層抽出
600 個內容；Opus 與 Codex 的 domain 判定 **495/600（82.5%）** 同值，
達到判定前凍結的 **0.75** 交叉門檻。這表示兩模型在同一批內容上
較常給出相同標籤，**不等於標籤已由人工驗證**。下表是 Opus 的
**模型標籤加權母體估計**，不是校內真實用途分布：

| 模型 domain 標籤 | 樣本內容 n／600 | 相異內容加權估計（分母 17,365；95% CI） | 請求比值估計（分母 58,100；95% CI） |
| --- | ---: | ---: | ---: |
| clinical（醫療照護） | 34 | 6.3%（4.3–8.3%） | 1.9%（1.2–2.6%） |
| teaching（教學與課程） | 139 | 26.1%（22.6–29.5%） | 10.7%（8.0–13.4%） |
| software（程式與系統開發） | 98 | 13.9%（11.5–16.4%） | 28.2%（20.1–36.2%） |
| infrastructure（系統維運與測試） | 41 | 7.4%（5.2–9.5%） | 7.3%（2.4–12.1%） |
| research（研究與分析） | 139 | 23.6%（20.2–27.0%） | 24.2%（16.2–32.2%） |
| general（一般事務） | 73 | 11.3%（8.9–13.8%） | 11.2%（5.4–17.0%） |
| unknown（無法判定） | 63 | 9.9%（7.7–12.1%） | 16.1%（6.7–25.6%） |
| not_applicable（不需判定） | 13 | 1.5%（0.4–2.5%） | 0.5%（0.2–0.8%） |

分項佔比各自四捨五入至一位，請求欄相加可能與 100% 差 0.1 個百分點。

樣本依 `unit_type × 內容長度分位` 分層，相異內容估計用各層
`母體內容數／抽中內容數` 加權；請求估計再帶入每個內容的重複請求數，
以比值調整校正至已知的 **58,100** 筆。未校正的類別請求估計合計
105.8%，不可當分布。兩欄的 95% 區間只含抽樣誤差，不含模型錯判、
文字截斷或未交付資料；請求欄比內容欄更不精確，例如 unknown 的
請求區間寬 18.9 個百分點。每筆最多送開頭 1,200 字元，樣本中
281/600（46.8%）被截斷（見 [DOMAIN_CROSS_RESULTS.md](DOMAIN_CROSS_RESULTS.md)
與 [INDEX.md](INDEX.md)）。

兩種單位回答的不是同一件事：在這份加權模型估計裡，teaching 佔相異內容
26.1%、佔請求 10.7%；software 分別為 13.9% 與 28.2%。同一內容反覆請求
會提高請求佔比，不會增加相異內容佔比；不能把一欄當另一欄的替代。

### 4.5 無法判定與尚未釐清的邊界

`unknown` 在樣本中為 **63/600**，加權相異內容估計 **9.9%**
（95% CI 7.7–12.1%），表示「無法判定用途」的份額，不是另一種用途。
兩模型對此值同判 **32/63（50.8%）**；不拆解，也不重新分配至其他值。

`not_applicable` 的事前預期是 **0**：母體已排除四條前置規則。
實際 Opus 判 **13/600**，Codex 同判 **9/13**；13 筆均未命中既有規則。
這可能涉及規則未涵蓋的形態，也可能是模型判讀邊界，現有檢查不能裁定。
逐筆與群層的非明文盤點留在 [DOMAIN_CROSS_RESULTS.md](DOMAIN_CROSS_RESULTS.md)；
事前零值預期與退回條件見 [FREEZE_2026-09.md](../ref/FREEZE_2026-09.md)。

因此第四節報告的是可重現的前置規則、失敗的分流檢查、以及附限制的
domain 探索性模型估計；它沒有形成經人工驗證的全量用途結論。

### 5.2 臨床資料的傳輸路徑

樣本中的臨床評分流程同時使用外部 API 與校內自建模型：評分階段使用
外部 API，事後分類階段使用自建模型。同一份內容經兩次傳輸，而原始
處理在外部。

此形態不支持「敏感內容留在校內」的描述。

### 5.3 憑證出現於日誌

校內自建服務的存取權杖以 query string 形式包含於網址中，隨客戶端
自動附加的瀏覽器狀態進入 gateway 日誌。

該權杖同時進入使用者的瀏覽器歷史與本日誌。

本專案的處理方式使該內容未進入任何衍生資料——`prompt_text` 僅落地
字元長度與雜湊值，明文不寫入 parquet。此為既有設計，非針對此情形。

### 5.4 使用者端的防護措施

樣本中出現兩項由使用者自行實作的機制：

- 一項自建工具的功能清單包含「送出前隱私確認」
- 一項面向學生的問答服務自訂了嚴格的回答邊界規則——不得加入知識來源
  中未載明的事實、數字、地點與電話；知識來源無法回答時須明確拒答

gateway 未提供對應機制。

## 六、已知限制

### 6.1 粒度

本分析的最小可靠層級為學院。

原因為帳號遮罩。遮罩替換帳號末三碼，對學生而言該三碼為班級序號，故
同系、同學位、同入學學年的使用者在遮罩後無法區分。119 個相異遮罩帳號
中有 39 個對應到多於一個識別碼。

因此無法回答的問題包括：

- 特定個人的使用量與成本
- 同一遮罩帳號底下是一人多次使用或多人各自使用
- 系所層級的分布（代碼 03、04 各對應兩個系所，區別鍵已被遮罩）

方向為單向：不同的遮罩帳號可確定非同一人；同一遮罩帳號無法確定為
同一人。故 275 這個人數為上界，實際人數只會更少。

各單位的人均指標受此影響——分母為識別碼數而非人數，而集中度高的單位
其人均主要由單一群組構成（見 2.2）。

### 6.2 成本

金額為已交付資料的牌價等值，非實際帳單，也非全量；
價目與帳單的其他差異見 3.1，上游未交付記錄見 6.5。

價格來源的可靠度：78.43% 使用官方明列價，13.55% 使用推估價，7.05%
為有時效的促銷價，0.97% 的模型名稱與價目列對應存在歧義（見 3.5）。

推估價的部分全部來自單一項目：gpt-5.6-sol 於 2026-08-22 降價前的
快取寫入價。官方頁面僅列現價，該日之前的價格依同家族的一致規律推得。
此為本估算最大的單一不確定來源。

本指標與其他指標有一項性質差異：它是「資料 × 外部價目 × 取價時間」
的函數，而非僅為資料的函數。同一批資料在不同時間以更新的價目重算會
得到不同結果。取價日期為 2026-08-27。

### 6.3 期間

資料涵蓋 24 日，全部落於暑假期間。學期中的使用行為未在觀察範圍內。

期間內另有一次 73.12 小時的服務中斷（見 5.5），以及首日與末日的
結構性截斷（見 1.1）。上游過濾另使三個擷取目錄日期的流量不完整，
與服務中斷、匯出視窗截斷分屬不同機制（見 6.5）。

7 月另有一批資料（2026-07-21 至 07-23、9,937 筆），schema 不同：該批
含 `turn_id`，可還原對話結構，故 6.4 第一項的限制在該批不存在。

兩批不可合併為連續序列，有三層原因。**識別碼不同種**：該批為本地指派的
序號（98 個），本批為上游計算的匿名雜湊，兩者無對應關係。**可對應的
層級只有遮罩帳號**——該批的 50 個遮罩帳號中有 44 個也出現在本批的 119
個裡，但遮罩帳號是多對一，個人層級接不起來。**期間亦不連續**：該批止於
07-23，本批始於 07-30。

該批的分析見 [RESULTS.md](RESULTS.md)。

### 6.4 可改善項目

以下三項若取得對應資料即可改善，均非分析方法的限制：

**對話結構。** lite schema 不含 `turn_id`，故無法判定單次使用者操作
內部的請求展開情形，亦使部分請求因缺乏前後文而無法判定用途（見 4.5）。
若後續匯出保留該欄位，此部分可回復。

**帳號的單位資訊。** 教職員帳號不編碼所屬單位（見 2.3），120 個識別碼、
22,524 筆請求因此無法歸屬。此為上游帳號系統的欄位設計，須由上游提供
對應資料方能解決。

**服務級距。** 日誌不含 `service_tier`，本估算假設全部為 Standard。
若實際使用批次或彈性級距，估算高估約一倍（見 3.1）。

- [`docs/INDEX.md` 的成本指標特別說明](INDEX.md#成本指標的特別說明)

### 6.5 上游交付與文字可見範圍

**上游未交付。** 23 份批次報告合計 `source_files` **141,619**；其中
`written_records` **120,520**、`excluded_internal_prompts` **21,099**
（14.90%），其餘跳過與失敗均為 0。US$2,749.32 不含被排除記錄的
成本；這些記錄沒有 token 用量，缺口大小無法估算。
有排除的 `date_dir` 是 **07-30、08-03、08-04**，分別排除
13,585、7,446、68 筆。`date_dir` 是 UTC 擷取目錄日期，**不是**
`date_taipei`；被排除記錄沒有時間戳，不能把缺口精確配到台北日期。
詳細平帳與日期對照見 [UPSTREAM_FILTER.md](UPSTREAM_FILTER.md)。

**已交付記錄的內容缺值。** 120,520 筆中另有 **241 筆**同時缺
`prompt_text_sha256` 與 `prompt_text_len`；長度是缺值，**不是 0**。
4.2 的 120,279 筆有內容請求已扣除這 241 筆，不能再扣一次。
這是保留記錄的欄位缺值，不是上游 21,099 筆未交付記錄的一部分
（見 [annotation_protocol.md](../ref/annotation_protocol.md)〈可分類母數 17,365 的可分類性上限〉）。

**可見文字只涵蓋請求的一段。** lite 只提供 `request.prompt_text`，
不提供 system、instructions 或對話歷史的內容；即使 sha256 與長度都有值，
也不能據此認定使用者的完整要求已可見。這與前兩項是不同層次的缺口，
三者不能相加成一個「資料遺失率」。clean 的 7 月批次在本機沒有等價批次
報告，9,937 筆僅能與本機檔數平帳，無法外證上游交付是否完整
（見 [UPSTREAM_FILTER.md](UPSTREAM_FILTER.md)）。

### 管線

```bash
python -m src.extract_lite                         # L1：原始 JSON → parquet
python -m src.schema_lite                          # 契約驗證
python -m src.aggregate_lite                       # L2：人層級表與集中度
python -m src.run metrics --line lite --publish    # 指標，並發佈到 docs/

python -m src.classify_lite.markers                # 用途分類前置：掃結構標記
python -m src.classify_lite.prefilter              # 用途分類前置：套四條規則
```

最後兩支**不在主管線裡**，單獨執行。第一支讀原始 JSON（約 3.5 分鐘），
第二支只吃它的輸出（秒級）。詳見 `RUNBOOK_lite.md` 情境三。

原始日誌不在版控內（體積與個資），需另行取得後放進 `data/00_raw_lite/`。
