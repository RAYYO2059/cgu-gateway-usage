# 指標索引

指標的定義、分母與注意事項都在這裡。標記之間的表格由
`python -m src.render_index`（clean）與 `python -m src.render_lite`（lite）
從 `src/metrics/registry.py` 的註冊表產生，請勿手動編輯——要改內容請改指標的
`@metric` 參數。標記以外的導覽是手寫的。

## 兩份結果文件，兩個問題

| 文件 | 資料 | 回答的問題 |
| --- | --- | --- |
| [RESULTS.md](RESULTS.md) | 1.8 天、9,937 筆 | 一個 turn 內部發生了什麼 |
| [RESULTS_lite.md](RESULTS_lite.md) | 24 天、120,520 筆、357 個 uid（275 人） | 誰在用、花了多少 |
| [CLASSIFICATION_LIMITS.md](CLASSIFICATION_LIMITS.md) | 225 群描述性分流、58 群跨模型判定、30 群人工標註 | 「做什麼」目前不能往下推到哪裡，以及為什麼 |

**這不是舊版與新版的關係。** 兩批資料的 schema、期間、母體都不同，各自回答
的問題也不同，而且**互相支撐**：

- lite 算出快取讀寫合計佔成本 **47.2%**（$782.47 + $515.79，總額 $2,749.32）。
- 解釋「為什麼會這樣」的機制在 clean 那份裡——agent 迴圈每一輪都要重送整段
  對話歷史，所以第二輪之後幾乎全部命中快取，token 膨脹中位數 52 倍。

沒有 lite，不知道那個機制花了多少錢；沒有 clean，不知道那筆錢為什麼會長成
那個形狀。

### 有三個指標 lite 永遠做不出來

`cache_hit_by_request_position`、`turn_expansion_depth`、
`token_inflation_by_client_type` 只存在於 clean，**不是因為 lite 的資料量不夠，
是因為 lite 的 schema 沒有 `turn_id`**。turn 與 thread 兩層要靠
`turn_id` / `thread_id` 的父子關係組出來，lite 匯出只有 `thread_id`。

所以 clean 那份不會被 lite 取代，即使它只有 1.8 天。它是這個專案唯一能講
**機制**的資料，而機制不依賴樣本量。

- 單一使用者佔該組流量 > `DOMINANT_THRESHOLD`（30%）

### 分組指標與抑制（lite）

<!-- AUTOGEN:SUPPRESSION_LITE:START -->
宣告了 `group_by` 的指標共 5 個，其中 3 個受抑制、2 個依政策豁免。

**受抑制的維度**

只有**把人分群**的維度才抑制：`account_type`、`unit`、`college`、`degree`、`entry_year`、`dept_code`、`request_style`。
依 `runs/<run_id>/concentration_lite.csv` 判定，觸發任一條件即抑制：

- 分組人數 < `MIN_GROUP_SIZE`（10）
- 單一使用者佔該組流量 > `DOMINANT_THRESHOLD`（30%）

觸發時該列的比例欄位置為 NA，**計數欄位保留**。
計數是事實，比例才有再識別與誤導風險。

**豁免的維度**

抑制它們只會把事實抹掉——「凌晨 3 點只有 2 個人在用」本身就是要報的事實，
清成 NA 反而讓讀者以為資料缺漏。

### 共通注意事項

- 這是**模型產生的描述性分類結果，無獨立參考標籤**，不得寫成「已驗證分類」。
- 118 群曾三度用於調參，是開發資料，不是驗證集。225 群的結果也因此不可
  重新包裝成獨立驗證集。
- 預先訂定的 `default` 共現檢查中，兩組各至少有一個方向低於 90%：
  `batch_project`／`all_three` 為 139/163（85.3%）與 139/146（95.2%）；
  `user_envelope`／`invocation_only` 為 30/37（81.1%）與 30/54（55.6%）。
  依預先訂定的門檻，結論是**「這一批判定不可信」**；此判定不因事後解釋
  而改變。
- `confidence` 是模型自評，不是經校準的信心值；三次執行的比例極差為
  **15.3pp**，不可拿來當信心值或不確定度。
- `insufficient` 只有 **n=1 群**。依 `MIN_GROUP_SIZE=10` 只出計數、不出比例。
  零或極低本身是結論，必須明列，不得省略；處理方式同
  `status_and_errors` 明列 429／402／403 為零。
- `reason` 欄的隱私保護只擋長字串的逐字重疊，不是語意層級檢查；不可據此
  宣稱該欄已完成語意去識別或沒有隱私風險。

## 欄位說明

- **單位**：這個指標的分析粒度（request / turn / thread / user）。
- **來源表**：實際讀哪張表計算。lite 只有 request 與 user 兩張。
- **分母**：比例的母體是什麼。分母講不清楚的比例不能用。
- **覆蓋率**：最近一次執行時，母體中實際有值的比例。
  尚未執行過的指標標示為「未執行」。

## 成本指標的特別說明

四個 `cost_*_lite` 指標的可重現性性質**與其他指標不同**。其他指標都是資料的
函數：資料不變，重跑必然得到一樣的數字。成本是「資料 × 外部價目 × 取價時間」
的函數，所以同一批資料在不同時間重算得到不同數字**不是 bug，是性質**。

要重現一份成本數字，必須同時固定資料與 `ref/pricing_table.csv` 的內容；
可重現性綁在該表的 `fetched_at` 上，不綁在資料上。引用成本數字的文件請一併
註明取價日期。

各指標 caveat 欄裡的另外三條限制（service_tier 假設、區域加價未計、促銷價
時效）說明的是**這個估算與實際帳單的系統性差距**，不是精度問題——那三項在
lite 資料裡沒有對應欄位，無法從資料判斷。
