> 這份檔案定的是**在看到任何結果之前**就該定下來的東西：座標、規則、退回門檻。
>
> 建立：2026-09-06

## 一、凍結座標

這五項一旦變動，之前算出來的任何比例都不能再跟之後的比。每一項附一句
「它變了會怎樣」，因為變動本身不會報錯——只會讓兩批數字看起來可以比較。

### 母體指紋

```
63af7d40e051d069dece9f14771eab6be7cb487f25c1937f6ff56ec12eb6919b
```

17,365 個相異內容的 `prompt_text_sha256`，**排序後以 `"\n".join` 串接再取
sha256**。串接方式是定義的一部分：無分隔串接會得到另一個值
（`ec123e0d8d76ae06ae51d95f383eff89347d16b96f9d7c37724e4dbab2b4b8dd`），
兩者都對，但只有一個是這裡說的那個。

母體來自 `runs/2026-09-05T1700_prefilter/classify_lite/prefilter_hits.parquet`
的 `rule == "需送分類器"`，即四條前置規則之後剩下的部分。

**它變了會怎樣：** 分類母數變了，所有以 17,365 或 58,100 為分母的比例全部
失效。而且是靜默的——比例照樣算得出來，只是分母換了人。抽樣當時的母數
是 17,368（舊版 request 層 prefilter），與現在差 3；那 3 筆的差異已經足以
讓「四項相加加上剩餘等於總數」對不起來。

### 長度切點

```
[251, 986, 4799]
```

分位定義：`Q1 <= 251 < Q2 <= 986 < Q3 <= 4799 < Q4`。

這組值是 17,365 個相異內容的 `prompt_text_len` 四分位。**現行母體重算的
結果與抽樣當時逐位相同，零列換分位**——所以固定它沒有損失，而重算會讓
「切點是資料的函數」變成每次都要重新記錄的東西。

**它變了會怎樣：** 24 個分層的成員換人，加權準確率的權重跟著換，而且
`baseline.py` 的門檻也是這個 Q1，基準線會一起飄。

### 聚類參數

| 參數 | 值 |
| --- | --- |
| 門檻（成群的最小相異內容數） | 10 |
| 階梯 L | `[4000, 2000, 1000, 500, 250, 120, 60, 30]` |
| 前綴上限 | 4000 字元 |
| 正規化 | 連續空白收斂為單一空格；連續數字換成單一 `0` |

門檻 10 的選擇有量尺：在**已知答案**的 5,437 筆（四支指紋流水線）上，
門檻 20/10/5 的召回率是 94.10% / 97.37% / 98.62%，而**錯併的絕對數三者
都是 2 筆**（同樣的兩群、同樣各混進 1 筆）。降門檻沒有增加錯併，只增加
要人工看的群數（51 → 103 → 200）。10 是召回率與人工成本的折衷。

**它變了會怎樣：** 群集清單整個換掉，`clusters.parquet` 的 `group_id`
不再指同一批內容，已完成的審閱紀錄全部作廢。門檻 20 的 `C01` 有 987 個
相異內容，門檻 10 的 `A001` 只有 974——**編號看起來對得上，內容不是同一批**。
這也是為什麼編號從 C/D 改成 A/B。

### 群集清單

226 群：`A001`–`A123`（無指紋母體）、`B001`–`B103`（有指紋母體）。
涵蓋 11,657 個相異內容 / 32,429 筆請求；散筆 5,708 / 25,671。

檔案：`clusters.parquet`、`cluster_members.parquet`（repo 外，不含明文）。

代表的選法：**群內內容長度最接近中位數的那一筆**；平手取較短，再平手取
sha256 字典序小的。頭尾兩端容易是異常值，中位數那筆最能代表常態。
選法必須是決定性的，否則中斷續跑時螢幕上的代表會換人，而審閱紀錄
記的還是同一個 `group_id`。

**它變了會怎樣：** 審閱時看到的東西換了，但 csv 裡的 `group_id` 沒變——
事後無從發現判斷依據已經不同。

### 基準線

`src/classify_lite/baseline.py`，門檻 `HUMAN_CHAT_MAX_LEN = 251`。
凍結的預測分布（17,365 個相異內容 / 58,100 筆請求）：

| 預測 | 相異內容 | 請求數 | 內容佔比 | 請求佔比 |
| --- | ---: | ---: | ---: | ---: |
| `not_human_chat` | 11,657 | 32,429 | 67.13% | 55.82% |
| `human_chat` | 3,682 | 18,974 | 21.20% | 32.66% |
| `abstain` | 2,026 | 6,697 | 11.67% | 11.53% |

**它變了會怎樣：** 基準線是分類器要打敗的對象。事後調過的基準線無法排除
是照著分類器的結果調的，那時它就不再是獨立的比較對象。`verify_frozen()`
是用來發現它飄掉的，不是用來更新它的。

## 二、審閱與標註規則

### 不預判

- **不預填、不顯示建議答案、不排序暗示。** 三個軸的值域列出來給人挑，
  但沒有預設值——預設值會變成錨點，而這一輪要的正是未被錨定的判斷。
- 載具的 `FIELDS` 只有值域沒有 default，`FIELD_HELP` 的每個值都有說明
  但沒有哪一個被標成推薦。有測試在守這件事。

### 空白不是答案

- 不確定要**明寫 `unsure`**，不能留空。空值會變成「跳過」的偽裝，而跳過
  與「我判斷是不確定」是兩件不同的事，事後從 csv 分不出來。
- 要跳過按 `s`（不寫入，下次還會出現）；要離開按 `q`（已審的都已寫入）。

### 審閱順序

1. `A001` 永遠第一——它單獨影響已發表的 `OVERVIEW` 4.2 那組數字。
2. 其餘按 `前綴佔中位內容長度比例` 由高到低。
3. 比例相同時按相異內容數由大到小。

**不是按規模排序。** 比例高的群，外框就是任務本身，看一眼就能判；先審
這些能在碰到模糊案例之前建立對這批資料的常態感。比例低的群外框只是信封，
判斷成本高，留到後面。規模大的群不一定好判——`A001` 有 974 個相異內容，
前綴卻只佔內容的一成，正是最難判的那一類。

### 批次與疲勞

- **一次最多 3 批，每批 10 個單位。** 超過就停，隔一段時間再來。
- 每個單位的耗時由載具自動記錄（`elapsed_sec`）。
- **耗時驟降或 `unsure` 率驟降是疲勞訊號，不是熟練。** 熟練會讓耗時緩慢
  下降並趨於平穩；疲勞是突然變快、而且不再標 `unsure`——因為判斷變成了
  猜測，而猜測比判斷快。看到這個形狀就停，那一批之後的紀錄要重做。
- 每批之間不要回頭改前一批。要改就整批重做並記下理由。

### 一致性抽驗

- 每完成 5 批，從已審的群裡隨機抽 10% 重審一次（不看第一次的答案）。
- 兩次的一致率就是下一節的「自我一致率」。

## 三、退回門檻

**這一節在看到任何結果之前定下。** 事後訂的門檻無法排除是照著結果訂的。

| 條件 | 處置 |
| --- | --- |
| 自我一致率 < 0.80（任一軸） | **退回改字典，不跑分類器。** 人自己都對不上，模型對得上也沒有意義 |
| `UNCERTAIN` 率 > 20%（任一軸） | 該軸**不出比例，只做描述**。分母裡有兩成是「不知道」時，比例的誤導性大於資訊量 |
| 分類器加權一致率 < 0.70 | 該軸**不進報告** |
| 0.70 – 0.85 | **只出粗分類**（合併相近的值），不出細項比例 |
| ≥ 0.85 | 可出比例，**仍附混淆矩陣** |
| 任一類別 n < 10 | **只出計數不出比例**（沿用 `config.MIN_GROUP_SIZE`） |
| 分類器未勝過 `baseline.py` | 該軸的內容分類**不算有貢獻**，報告中據實說明 |

「加權」指以 24 個分層在母體裡的佔比加權。**四個分層在 150 筆舊驗證集裡
沒有樣本**（`服務憑證|Q3|重複`、`教職員|Q4|重複`、`服務憑證|Q4|重複`、
`服務憑證|Q4|單次`，合計 145 個相異內容、佔母體 0.84%）——那 0.84% 的加權
準確率是**無定義**，不是 0。新抽樣要處理這件事。

「勝過基準線」的定義：在同一組人工標註上，分類器要麼在 `abstain` 那
2,026 筆（佔母體 11.67%）上真的判得出東西，要麼在另外兩桶上比基準線更準。
兩者都做不到，就代表這一輪的內容分類沒有帶來新資訊——**那是個結論，
不是失敗**，而且是個省錢的結論。

## 四、為什麼這份檔要進版控

門檻的可信度來自它**在資料之前就存在**。

一個 0.85 的門檻，若是在看到分類器跑出 0.87 之後才寫下來的，它就不是門檻，
是事後的合理化。而從結果上看，兩者長得一模一樣：同樣的數字、同樣的措辭、
同樣的「我們早就決定了」。**沒有任何方法能從文件內容分辨這兩者。**

git 的時間戳是唯一的證據。這份檔案先於標註與分類進版控，之後任何人
（包括寫它的人）都可以用 `git log` 確認它不是倒填的。

同樣的理由，這份檔案**不放在 `docs/DESIGN_NOTES.md`**（那份不進版控），
也不寫在對話紀錄裡（那些會消失，而且無法佐證先後）。

`ref/` 是白名單制（`ref/*` 擋全部、逐項放行），所以這份檔案需要在
`.gitignore` 裡明確放行才進得了版控——被 ignore 的檔案不會出現在
`git status`，會安靜地留在本機直到有人 clone 之後點不到。
