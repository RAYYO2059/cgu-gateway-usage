把校內 AI gateway 的 API 請求日誌整理成一批可重跑的使用統計：誰在用、拿它做什麼、怎麼用。

三件事先講在前面，因為它們決定了你能從這批數字得到什麼：

1. **只有 1.8 天**，而且頭尾兩天都不完整。跨到 3 個分區只是因為橫跨了兩個午夜。
2. **98 個人是下界不是精確值**。帳號末三碼被遮罩成 `XXX`，同前綴的不同人會被合併。
3. **只看得到結構，看不到內容**。抽取時刻意只保留字元長度，原文不進表。

## 這批資料不能說什麼

這些不是免責聲明，是實際踩過的坑。每一條都對應到某個看起來很合理、但會算錯的做法。

1. **不能談作息、尖峰或週期。**1.8 天的資料，其中兩天不完整，只橫跨 3 個 weekday 值。時段分布只能當成「這 1.8 天的請求落在哪些小時」的事實描述，不可外推、不可用來排容量。

2. **不能把 98 當成精確人數，也不能回推到個人。**`username` 是 gateway 指派的人員層級 ID，比被遮罩的帳號可靠，但遮罩本身無法還原——同前綴的不同人已經合併了。43 個學生、44 個教職員、11 個服務憑證，服務憑證不是人，做人均統計必須先剔除。

3. **不能用請求數當使用量。**agent 會把一次使用者動作展開成多次 API 呼叫：1,025 個 turn 產生了 9,937 個請求。展開深度的 p50 是 **1**、mean 是 **6.94**、max 是 199——用平均值會把「一半的動作只發一個請求」這件事完全蓋掉。問「打了幾句話」看 turn，問「做了幾件事」看 thread。

4. **不能直接加總 token。**兩個獨立的理由：一是快取命中的前綴每次都重新計入 `prompt_tokens`，中位請求因此高估 **52 倍**（p90 高估 341 倍）；二是有 188 筆請求的用量根本沒被記錄，其中 102 筆是 status=200 的串流請求，`total_tokens` 記成 0 但實際不是 0，直接 sum 會把它們當成零消耗。所有 token 統計都排除了這 188 筆，並在輸出中註明排除數。

5. **幾乎所有「某族群佔 X%」都不能說。**學生分組的比例欄位 100% 被抑制——不是計算失敗，是母數太小或單人佔比過高。直呼那一組更明顯：25 個人裡有一個人佔了該組 61.0% 的請求、83.6% 的 token，那一組的「平均行為」基本上是一支腳本。相對地，計數一律保留：「16 個系所有人使用」可以說，「某系所佔 45%」不行。

6. **不能說使用者拿它做了什麼。**端點能區分對話／語音／轉錄／生圖，但同一個 `/v1/responses` 可能是寫程式也可能是翻譯。工具欄位只有**類別**沒有名稱，而且是**宣告掛載**不是**實際呼叫**——掛了 web_search 不代表真的搜尋過，資料裡沒有任何欄位能分辨這兩件事。

7. **有些「一致」只驗到一半。**模型替換率 0.01% 是拿 gateway 自己的兩個欄位比出來的。用第三個欄位 `response_model` 獨立勾稽後，1,958 筆可比對的請求 100% 一致——但這 1,958 筆**全部是直呼流量**，7,115 筆 Codex 請求一筆都沒有這個欄位。佔七成的主要流量仍然無法獨立驗證。

反過來，有一件事可以講得很肯定：**429、402、403 全部是零筆**。這段期間沒有任何技術性額度阻擋，所以「某人用量低」不能被解釋成「他被擋住了」。

## 重跑

```
python -m src.run all        # extract → validate → aggregate → metrics
```

單獨跑某一步：

```
python -m src.run extract    # 原始 JSON → 分區 parquet（增量，只處理變動過的檔）
python -m src.run validate   # schema 檢查 + 產生 ref/user_registry.csv
python -m src.run aggregate  # request → turn / thread / user + 集中度檢查
python -m src.run metrics    # 執行全部指標，順帶更新 docs/INDEX.md 與本檔
python -m src.run metrics --publish  # 額外更新 docs/RESULTS.md、docs/data/、docs/figures/
python -m src.run audit      # 欄位稽核：原始 JSON 有但沒抽的欄位（不納入 all）
```

`audit` 刻意不納入 `all`：它要掃全部原始 JSON，比其他步驟慢一個量級，而且只有在懷疑上游改過欄位時才需要跑。

每次執行的快照落在 `runs/<run_id>/`，指標輸出落在 `runs/<run_id>/metrics/`。每個 run 目錄下還有一份 `run_manifest.json`，記著那次跑了哪些階段、成功還是半途失敗、當時的母數多少，要判斷某個快照完不完整直接看它就好，不用從檔案組成反推。這些都不進 git。

## 程式從哪裡讀起

`src/` 底下十幾個檔案，但主線只有六個，照資料流的順序看下去就懂了：

| 檔案 | 在做什麼 |
| --- | --- |
| `extract.py` | 把一檔一請求的原始 JSON 攤平成表。欄位對照表在這裡，想知道某一欄怎麼來的就看它。 |
| `schema.py` | 攤平之後立刻驗一次。型別、時區、不該是空字串的欄位，對不上就當場失敗。 |
| `identity.py` | 從被遮罩的帳號推出身分（學生／教職員、入學年、系所），順便產生 `ref/user_registry.csv`。 |
| `aggregate.py` | request 往上疊成 turn / thread / user 三張表，並算出每個分組被單一使用者佔了多少。 |
| `metrics/` | 指標本體。`registry.py` 是註冊與抑制機制，`basic.py`、`derived.py` 是那 19 個指標，一個函數一個。 |
| `render_*.py` | 把指標輸出寫成文件：`render_index` 管 INDEX 與本檔，`render_results` 管 RESULTS，`render_figures` 畫那三張圖。 |

`run.py` 只負責把上面這些接起來，自己不做事。要加新指標的話只要在 `metrics/` 裡多寫一個掛 `@metric` 的函數，抑制、覆蓋率、寫檔都會自動套用。

## 這個 repo 沒有原始資料

`data/00_raw/` 是空的，也不會有東西——原始日誌含個資，整個 `data/` 都在 `.gitignore` 裡。所以 clone 下來直接跑 `python -m src.run all` 會在驗證那一步停下來，告訴你 `data/01_request` 沒有資料、要先把日誌放進 `data/00_raw/`，然後以錯誤碼結束。這是預期行為，不是壞掉。

要真的重跑，得自己把 gateway 的 log 放進 `data/00_raw/<日期>/`，一個請求一個 JSON 檔。`ref/user_registry.csv` 同理，那是 `validate` 階段自己生出來的，不進版控。

`docs/` 底下的數字和圖是某一次執行的快照，不是即時的。想知道那次跑了什麼，看 `runs/<run_id>/run_manifest.json`——不過 `runs/` 也不進版控，所以你看到的快照只有 `docs/` 這一份。

本檔的三個 `AUTOGEN` 區塊由 `python -m src.render_index` 產生，區塊以外的文字不會被覆寫。`docs/INDEX.md` 整份都是產生的，要改內容請改指標的 `@metric` 參數。`docs/RESULTS.md` 只有 `AUTOGEN` 區塊是產生的，其餘散文是手寫的。
